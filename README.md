# 工程监理公司-异常申诉复核旁站记录单系统

基于 **Remix + Koa + SQLite** 构建的工程监理旁站记录全流程管理系统。

## 系统概述

本系统实现工程监理旁站记录从登记、审核到复核归档的完整业务流程，重点关注旁站记录单的连续处理能力，支持多种异常场景处理。

### 核心角色

| 角色 | 用户名 | 密码 | 职责 |
|------|--------|------|------|
| 旁站记录登记员 | registrar1 / registrar2 | 123456 | 发起旁站记录、补正材料、再次提交 |
| 旁站记录审核主管 | supervisor1 / supervisor2 | 123456 | 审核旁站记录、提出补正要求、标记异常 |
| 工程监理公司复核负责人 | reviewer1 / reviewer2 | 123456 | 最终复核、归档、裁定状态冲突 |

### 业务流程

```
旁站记录登记员
      ↓
  起草/创建记录 → 提交审核
      ↓
旁站记录审核主管
      ↓
  ┌─────────────┬───────────────┬──────────────────┬───────────────┐
  ↓             ↓               ↓                  ↓               ↓
审核通过     审核驳回       退回补正         标记缺证据     标记状态冲突
  ↓             ↓               ↓                  ↓               ↓
  │         登记员整改       登记员补正         补充证据       现场核实
  │             └───────────┐    │                  │               │
  │                         ↓    ↓                  ↓               │
  └──────────────→     再次提交   ←─────────────────┴───────────────┘
                              ↓
                     重新进入审核流程
                              ↓
工程监理公司复核负责人
                              ↓
                    ┌─────────────┐
                    ↓             ↓
                复核通过       复核驳回
                    ↓             ↓
                  归档        退回重审
```

### 状态说明

| 状态 | 说明 | 颜色标识 |
|------|------|----------|
| 草稿 | 登记员新建未提交 | ⚪ 默认 |
| 已提交待审核 | 已提交，等待审核主管处理 | 🔵 蓝色 |
| 审核中 | 审核主管正在处理 | 🟡 处理中 |
| 审核通过 | 审核主管审核通过，等待复核 | 🟢 成功 |
| 审核驳回 | 审核主管驳回，需整改后重新提交 | 🔴 错误 |
| 需补正 | 审核主管要求补充材料 | 🟠 警告 |
| 已补正 | 登记员已补正，等待再次审核 | 🔵 蓝色 |
| 复核中 | 复核负责人正在处理 | 🟡 处理中 |
| 复核通过 | 最终复核通过，可归档 | 🟢 成功 |
| 复核驳回 | 最终复核驳回 | 🔴 错误 |
| 缺证据 | 缺少必要的证据材料 | 🟠 警告 |
| 逾期 | 超过处理截止时间 | 🔴 红色 |
| 状态冲突 | 多方反馈状态不一致，需现场核实 | 🟣 洋红 |
| 已归档 | 流程完成，已归档 | ⚪ 默认 |

## 技术栈

### 前端
- **Remix 2** - 全栈 React 框架
- **React 18** - UI 库
- **TypeScript** - 类型安全
- **Ant Design 5** - UI 组件库
- **Vite** - 构建工具

### 后端
- **Koa 2** - Node.js Web 框架
- **@koa/router** - 路由
- **sql.js** - SQLite 数据库驱动（纯 JS 实现，兼容 Node 20+，无需 C++ 编译）
- **jsonwebtoken** - JWT 认证
- **bcryptjs** - 密码加密
- **dayjs** - 日期处理

### 数据库
- **SQLite 3** - 本地文件数据库（sql.js 纯 JS 驱动，无需额外安装）

系统默认端口：

### 修改端口

如需修改端口，可通过环境变量配置：

#### 后端端口修改
```bash
# 修改 backend/.env
PORT=8004  # 改为需要的端口

# 同时需要修改前端 vite.config.ts 中的代理配置
# 修改 frontend/vite.config.ts
const DEFAULT_BACKEND_PORT = process.env.BACKEND_PORT || '8004';
```

#### 前端端口修改
```bash
# 修改 frontend/.env
FRONTEND_PORT=3004  # 改为需要的端口
BACKEND_PORT=8004   # 需与后端端口保持一致

# 修改 frontend/vite.config.ts
const DEFAULT_FRONTEND_PORT = process.env.FRONTEND_PORT || '3004';
```

## 快速开始

### 前置要求
- Node.js >= 18.0.0
- npm 或 yarn

### 1. 安装依赖

```bash
# 安装后端依赖
cd backend
npm install

# 安装前端依赖
cd ../frontend
npm install
```

### 2. 初始化数据库

```bash
cd backend

# 初始化数据库表结构
npm run init-db

# 插入样例数据（包含多种状态场景）
npm run seed-data
```

数据库文件将创建在 `backend/data/supervision.db`

### 3. 启动服务

```bash
# 启动后端服务（默认端口 8004）
cd backend
npm start
# 或开发模式
npm run dev

# 启动前端服务（默认端口 3004）
cd frontend
npm run dev
```

### 4. 访问系统

打开浏览器访问：http://localhost:3004

使用测试账号登录，查看不同角色的操作界面。

## 核心功能演示流程

### 流程演示：申诉提交 → 驳回 → 补正 → 再次提交 → 复核通过

以 **PZ-2024-003**（需补正）为例：

1. **登录登记员账号** (registrar1 / 123456)
   - 查看工作台，看到"需补正"待办事项
   - 进入 PZ-2024-003 记录详情，查看"上一处理人意见"橙色卡片
   - 查看补正要求：缺预埋件标高测量照片和焊缝质量检测报告
   - 点击【补正材料】按钮，弹窗内：
     - 顶部 Alert 自动显示上一处理人补正要求
     - 填写补正说明/处理意见
     - 点击【添加证据】新增照片证据（类型选photo，填名称、描述、文件标识）
     - 必须至少包含1份照片证据（前端+后端双重校验）
   - 提交后：状态→"已补正"，处理人切回审核主管，证据列表/审核历史/操作日志同步刷新

2. **补正后点击【再次提交】**（同一登记员可操作）
   - 操作：补正→再次提交
   - 状态从"已补正"流转回"已提交待审核"
   - 自动指派审核主管处理

3. **切换到审核主管账号** (supervisor1 / 123456)
   - 在工作台"待审核"列表中看到 PZ-2024-003
   - 进入详情页查看补正说明和新增证据
   - 点击【审核通过】，流转到监理公司复核

4. **切换到复核负责人账号** (reviewer1 / 123456)
   - 开始复核，查看完整的审核历史时间线和所有操作记录
   - 【复核通过】→ 状态变为"复核通过"
   - 【归档】→ 完成全流程闭环

### 异常场景演示

1. **缺证据场景** (PZ-2024-004)
   - 审核主管标记"缺证据"，已写入具体缺失内容：卷材搭接实测照片、基层含水率检测报告、热熔施工火候控制记录
   - 登录登记员2 (registrar2 / 123456)，在待办中看到该记录
   - 补正时必须补充至少1份photo类型证据
   - 后端校验：现有证据 + 本次新增证据 合并后是否包含photo类型

2. **逾期场景** (PZ-2024-005)
   - 登录审核主管2 (supervisor2 / 123456)，看到红色"已逾期"标记
   - 审核主管可选择：【逾期情况确认通过】/【逾期并审核驳回】/【逾期要求补正】
   - 每种操作都需填写处理意见

3. **状态冲突场景** (PZ-2024-009)
   - 登录登记员1 (registrar1 / 123456)，看到紫色"状态冲突"标记
   - 上一处理人意见：工程名称"城市高架桥工程"与部位"3#厂房机电管线预埋"不一致，要求核实
   - 登记员点击【补正材料】填写核实说明、补充设计变更证明
   - 补正后由复核负责人最终裁定是否通过

4. **版本冲突校验**
   - 当两人同时打开同一条记录进行操作时
   - 后端校验版本号(乐观锁)，先提交的成功（版本号+1），后提交的提示"版本冲突"
   - 保留原状态，写入操作日志便于追溯

## 后端校验机制

每次提交操作时，后端会严格校验以下内容：

### 1. 处理人校验
- 验证当前用户是否为记录的指定处理人
- 非处理人操作将被拒绝并记录日志

### 2. 角色权限校验
- 基于角色的访问控制 (RBAC)
- 每种操作只能由指定角色执行
- 例如：审核操作只能由审核主管执行

### 3. 状态流转校验
- 严格的状态机控制
- 每种状态下只允许特定的操作
- 例如：已归档的记录不能再进行任何修改

### 4. 版本号校验
- 每条记录带有版本号（version）
- 提交时必须匹配当前版本
- 防止并发修改导致的数据不一致

### 5. 必选证据校验
- 提交审核前必须包含至少1份照片证据
- 缺证据状态下补正时必须补充缺失的证据类型

### 6. 校验失败处理
- 校验不通过时，**保留原状态**不改变
- 写入操作日志，记录失败原因
- 返回明确的错误信息给前端

## API 接口

### 认证接口
- `POST /api/auth/login` - 登录
- `POST /api/auth/logout` - 退出
- `GET /api/auth/profile` - 获取当前用户信息

### 旁站记录单接口
- `GET /api/records` - 获取记录列表（支持分页、筛选）
- `GET /api/records/:id` - 获取记录详情
- `POST /api/records` - 创建记录
- `PUT /api/records/:id` - 更新记录
- `DELETE /api/records/:id` - 删除记录（仅草稿）
- `POST /api/records/:id/operate` - 执行操作（提交/审核/复核/补正等）
- `GET /api/records/statistics` - 获取统计数据
- `GET /api/records/options` - 获取下拉选项

### 操作日志接口
- `GET /api/logs` - 获取操作日志列表

## 操作日志

系统完整记录所有操作，包括：
- 操作时间
- 操作人及角色
- 操作类型
- 操作描述
- IP 地址
- 关联记录编号

操作日志不可修改、不可删除，用于审计追踪。

## 常见问题

### 1. 端口被占用
修改 `.env` 文件中的端口配置，确保前后端端口一致。

### 2. better-sqlite3 安装失败
better-sqlite3 需要编译原生模块，请确保系统已安装 Python 和 C++ 编译工具：
- Windows: `npm install --global windows-build-tools`
- macOS: `xcode-select --install`
- Linux: `sudo apt-get install build-essential python3`

### 3. 前端无法连接后端
- 确认后端服务已启动
- 检查端口配置是否一致
- 查看 vite.config.ts 中的代理配置
