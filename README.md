# 新闻采编中心 · 新闻线索管理系统

一个面向新闻采编中心的新闻线索登记、核实分派、回访归档全流程管理系统，支持异常申诉复核与多角色办理边界控制。

- **前端**：Nuxt 3 + Vue 3 + Pinia（端口 3002，可改）
- **后端**：Go 1.21 + Fiber v2（端口 8002，可改）
- **数据库**：SQLite（本地文件 `backend/news_clue.db`，自动建库+自动填充样例）

---

## 🎯 核心能力

### 办理边界（谁能办 · 谁只能看）

| 角色 | 可执行操作 | 可见范围 |
|------|-----------|----------|
| 📝 **新闻线索登记员** | 创建线索单、补充证据、提交/补正重提、发起异常申诉 | 仅本人登记的线索单 |
| 🔍 **新闻线索审核主管** | 核实分派、开始核实、标记缺证据、退回补正、完成核实提交复核 | 待分派+分派给自己的线索单 |
| 📋 **新闻采编中心复核负责人** | 复核归档、标记逾期、标记状态冲突、受理/驳回异常申诉 | **全部线索单**，重点看复核/申诉队列 |

### 流程主线
```
线索爆料（登记员登记/提交）
    ↓
核实分派（审核主管分派给审核人）
    ↓
核实办理（开始核实 → 缺证据/退回补正 ↺ 补正重提）
    ↓
完成核实 → 复核归档（复核负责人审批归档）
```
异常时可触发：**登记员发起异常申诉 → 复核负责人受理/驳回** 全闭环。

### 异常申诉状态机
```
退回补正 / 缺证据 / 逾期 / 状态冲突 / 已归档
                    ↓ 登记员发起申诉（申诉理由必填）
               异常申诉中（appealed）
              /        |          \
     驳回申诉       受理申诉      受理并转补正重提
          ↓            ↓               ↓
    申诉已驳回     申诉已受理       补正重提
                        ↓
                   登记员补正后再次提交 → 重新进入待分派
```
详情页中，**申诉理由、复核意见、驳回原因、原状态、所有操作记录**都会完整留痕。

## 🚀 快速启动（从零到跑通）

### 0. 环境要求
- Go >= 1.21
- Node.js >= 18
- npm（或 pnpm/yarn 可自行替换）

### 1. 建库 & 启动后端

后端首次启动时，**自动执行**：SQLite 建库 → 建表（AutoMigrate） → 插入 5 个用户 + 8 条多状态样例。

```bash
cd backend
# 1) 拉依赖
go mod tidy
# 2) 编译（可选，也可以 go run）
go build -o news-clue-server ./cmd
# 3) 启动，端口默认 8002，要改加环境变量 PORT
PORT=8002 ./news-clue-server
# 或不编译直接跑：
#   PORT=8002 go run ./cmd
```

✅ 启动成功看得到：
```
SQLite 已连接: ./news_clue.db
数据库表迁移完成
开始填充初始样例数据...
样例线索单填充完成，共 8 条...
服务启动，监听端口: 8002
```

> 📁 SQLite 数据库文件：`backend/news_clue.db`，删除即重置所有数据。

### 2. 启动前端

```bash
cd frontend
# 1) 安装依赖
npm install
# 2) 启动开发服务器，端口默认 3002
#    - 改前端端口：PORT=3003 npm run dev
#    - 改后端地址：API_BASE_URL=http://localhost:8003 npm run dev
npm run dev
```

启动后浏览器打开：**http://localhost:3002**

### 3. 切换端口演示

前端端口 `3002` 和后端端口 `8002` 都可以改，两边同步即可：

```bash
# 后端改 8003
PORT=8003 ./news-clue-server           # backend 目录下

# 前端改 3003 并指向新后端
PORT=3003 API_BASE_URL=http://localhost:8003 npm run dev    # frontend 目录下
```

> 💡 nuxt.config.ts 里已把端口、API base 都做成 `runtimeConfig.public`，通过 `process.env.PORT` / `API_BASE_URL` 注入。

## ✅ 推荐的演示流程

### 场景 A：完整的正常流转
1. 用 `registrar1` 登录，新建线索单填写并提交 → 进入「待核实分派」
2. 切 `auditor1` 登录，进入详情：**核实分派** 给自己 → **开始核实** → 填核实结论，**提交复核归档**
3. 切 `reviewer1` 登录，进入详情填归档结论，**复核归档** → 线索单到「已归档」

### 场景 B：退回补正 + 申诉闭环
1. 切到样例单 #4（培训机构那单，状态为退回补正），用 `registrar1`（登记人）登录
2. 详情页可选：
   - **补正材料后再次提交**（补充 1+ 份证据，带版本乐观锁校验）
   - 或 **发起异常申诉**（填写申诉理由） → 状态变「异常申诉中」
3. 切 `reviewer1` 登录进入同一条单据：可选 **受理申诉 / 受理并转补正重提 / 驳回申诉**
4. 若受理：登记员登录可在「申诉已受理」状态下补正后再次提交，重新走核实分派流程

### 场景 C：版本冲突 + 状态乐观锁
1. 浏览器里用两个不同角色同时打开同一条单据详情
2. A 窗口先做一次状态变更（版本号从 vN 升到 vN+1）
3. B 窗口再操作同一单据，提交时后端按 `version` 字段做乐观锁判定，前端会提示**版本冲突错误**，需刷新后重试

## 🛡️ 后端关键校验点

线索单每次状态变更，`handlers.go` 都会在事务内依次校验：

1. **当前处理人身份**（通过 JWT 反解）
2. **角色办理边界**（按角色 + 当前状态判断是否有权限）
3. **状态流转合法性**（限制允许的前→后状态迁移对）
4. **单据版本号**（乐观锁 `Version` 字段，冲突返回 409，保留原状态）
5. **必填证据 & 必填字段**（提交/补正重提时至少 1 份证据；退回/驳回必须填原因；归档必填结论）
6. **写操作记录**（任何状态流转都追加一条 `OperationLog`，包含：处理人/角色/前后状态/意见/原因/版本号）
7. **原状态留痕**（申诉记录里额外保存 `OriginalStatus`，详情页可完整溯源）

未通过校验时：**保留原状态** → 返回具体错误信息 → 操作记录**不会**被写脏。

## 📬 API 概览

| 方法 | 路径 | 说明 | 权限 |
|------|------|------|------|
| POST | `/api/auth/login` | 登录，返回 JWT | 公开 |
| GET  | `/api/auth/me` | 当前用户信息 | 已登录 |
| GET  | `/api/stats` | 大屏统计（按状态/角色） | 已登录 |
| GET  | `/api/clues?status=&role=&keyword=` | 线索单列表（按角色隔离） | 已登录 |
| POST | `/api/clues` | 新建线索单（草稿/提交） | 登记员 |
| GET  | `/api/clues/:id` | 详情（证据/操作/申诉全部） | 已登录+可见范围内 |
| POST | `/api/clues/:id/assign` | 核实分派 | 审核主管 |
| POST | `/api/clues/:id/process` | 通用处理（版本号必填） | 按角色判定 |
| POST | `/api/clues/:id/appeal` | 提交异常申诉（理由必填） | 登记员本人 |
| POST | `/api/clues/:id/appeal/review` | 受理/驳回申诉 | 复核负责人 |
| POST | `/api/clues/:id/resubmit-appeal` | 申诉受理后补正重提 | 登记员本人 |

所有需要写状态的接口请求体里必须包含 `version`（前端详情页加载时拿到，提交时原样带回），用于**后端乐观锁**。
