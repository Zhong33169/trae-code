# 维修服务平台 - 风险分级处置维修订单系统

基于 Solid.js + Vite 前端和 Go Fiber 后端的维修订单风险分级处置系统，实现完整的工单流转、风险分级、权限校验和操作追溯。

## 系统特性

### 办理边界
- **维修登记员**：发起工单、补正重提
- **维修审核主管**：师傅派单、完工验收、退回补正、标记异常
- **复核负责人**：复核归档

### 处理流程
```
报修登记 → 师傅派单 → 完工验收 → 复核归档
     ↓         ↓          ↓
  退回补正   缺证据      状态冲突
     ↓         ↓
  补正重提   标记逾期
```

### 风险分级（非标签，实际影响处理）
| 风险等级 | 优先级 | 所需证据 | 逾期后优先级 |
|---------|--------|----------|-------------|
| 🔴 高风险 | 90 | 4 份 | 120 |
| 🟡 中风险 | 50 | 2 份 | 80 |
| 🟢 低风险 | 20 | 1 份 | 50 |

- 队列按「是否逾期 → 优先级 → 创建时间」排序
- 高风险工单始终排在最前
- 逾期工单优先级自动 +30

### 后端校验逻辑
每次提交操作时，后端依次校验：
1. **当前处理人**：必须是当前登录用户
2. **角色权限**：角色必须匹配当前处理阶段
3. **订单状态**：状态必须符合操作要求
4. **版本号**：乐观锁防止并发修改
5. **必填证据**：证据数量必须满足风险等级要求

校验不通过时：
- 保留原订单状态不变
- 写入完整操作记录（含失败原因）
- 返回明确错误信息

### 样例数据（10 个订单，覆盖各种场景）
| 状态 | 说明 |
|------|------|
| ✅ 正常流程 | 已登记、已派单、已完工、已归档各阶段 |
| 📎 缺证据 | 证据不足，无法验收 |
| ⏰ 逾期 | 超期未处理，优先级提升 |
| ↩️ 退回补正 | 信息不全，退回登记员 |
| ⚠️ 状态冲突 | 系统状态与实际不符 |

## 快速开始

### 环境要求
- Go 1.21+
- Node.js 18+

### 端口配置
默认端口（TCP 端口有效范围 1-65535）：
- 前端：31010
- 后端：51010

如需修改：
- **后端**：修改 `backend/.env` 中的 `PORT`（需 ≤ 65535），或启动时 `PORT=51011 go run .`
- **前端**：修改 `frontend/.env` 中的 `VITE_PORT`（需 ≤ 65535），或启动时 `VITE_PORT=31011 npm run dev`
- 若后端端口变更，请同步修改 `frontend/.env` 中的 `VITE_API_URL`

> 注意：原要求的 81010 端口超出 TCP 端口最大值 65535，已调整为 51010。

```bash
cd backend

# 安装依赖

# 启动服务（自动建库 + 初始化样例数据）
```

### 3. 查看样例

打开前端页面后，通过右上角切换不同角色体验完整流程：

#### 演示流程 1 - 正常工单处理
1. **张登记**（维修登记员）- 「新建工单」创建一个高风险工单
2. 切换到 **王主管**（维修审核主管）
   - 点击新创建的工单，查看详情
   - 确认上一处理人意见（张登记的创建意见）
   - 选择「📤 师傅派单」，填写师傅信息，添加 2 份证据
   - 提交后，队列状态变为「已派单」，进入验收阶段
3. 仍作为 **王主管**，继续处理
   - 添加工单验收所需的剩余证据（高风险需 4 份）
   - 选择「✅ 完工验收」
   - 提交后，状态变为「已完工」，流转至复核负责人
4. 切换到 **陈复核**（复核负责人）
   - 查看完整操作记录和所有证据
   - 选择「📦 复核归档」
   - 工单完成全流程

#### 演示流程 2 - 退回补正
1. 用 **王主管** 打开一个「已登记」状态的工单
2. 选择「↩️ 退回补正」，填写退回原因
3. 切换到 **张登记**，可以看到工单出现在待办中
4. 张登记补充证据后，选择「🔄 补正重提」
5. 工单重新回到审核主管待办

#### 演示流程 3 - 证据不足拦截
1. **王主管** 打开一个「已派单」的工单（证据只有 1 份，高风险需要 4 份）
2. 直接点击「✅ 完工验收」
3. 后端校验失败，返回：「证据不足，需要 4 份，现有 1 份」
4. 查看操作记录，可以看到失败的尝试已被记录

#### 演示流程 4 - 版本冲突（并发控制）
1. 打开两个浏览器窗口，都登录为 **王主管**
2. 同时打开同一个工单的详情页
3. 在窗口 A 中执行派单操作，成功后版本号 v1 → v2
4. 在窗口 B 中也执行操作，会提示「订单已被修改，请刷新后重试」
5. 刷新窗口 B 后可继续操作

## API 接口

所有接口需要 `Authorization: Bearer {用户ID}` 请求头。

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/health` | 健康检查 |
| GET | `/api/user/me` | 获取当前用户 |
| GET | `/api/users` | 获取所有用户 |
| POST | `/api/orders` | 创建工单 |
| GET | `/api/orders` | 获取工单列表（支持 status/risk/stage 过滤） |
| GET | `/api/orders/:id` | 获取工单详情（含证据、操作记录） |
| POST | `/api/orders/:id/process` | 处理工单 |
| GET | `/api/statistics` | 获取统计数据 |

### 处理工单操作类型

| 操作 | 角色 | 说明 |
|------|------|------|
| `dispatch` | 主管 | 师傅派单 |
| `return_to_registrar` | 主管 | 退回补正 |
| `complete` | 主管 | 完工验收（校验证据） |
| `mark_missing_evidence` | 主管 | 标记缺证据 |
| `mark_overdue` | 主管 | 标记逾期 |
| `mark_conflict` | 主管 | 标记状态冲突 |
| `re_submit` | 登记员 | 补正重提 |
| `archive` | 复核 | 复核归档 |

## 重新初始化数据库

如需重置所有数据：

```bash
# 删除数据库文件
rm backend/data/repair.db

# 重启后端服务，会自动重建并初始化样例数据
cd backend && go run .
```

## 核心校验逻辑说明

后端 `ProcessOrder` 函数完整校验流程（`backend/handlers/order.go`）：

```
1. 开启事务
2. 查询当前订单状态、版本、处理人
3. 校验当前处理人是否为登录用户 → 失败记录日志并返回
4. 校验角色是否匹配当前阶段 → 失败记录日志并返回
5. 校验版本号（乐观锁） → 失败记录日志并返回
6. 校验特定操作的附加条件：
   - 派单：师傅信息必填
   - 验收：证据数量 ≥ 风险等级要求
7. 若有新增证据，写入 evidences 表
8. 更新订单状态、版本号、优先级、处理人
9. 记录完整操作日志
10. 提交事务
```

所有校验失败的操作都会写入 `operation_logs` 表，保留完整审计痕迹。
