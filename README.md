# 养老护理院-跨班组交接确认护理计划单系统

## 系统简介

本系统是专为养老护理院设计的护理计划单跨班组交接确认管理系统，实现护理计划从登记、审核到复核归档的全流程电子化管理，确保跨班组交接信息完整可追溯。

### 核心功能

- **三角色审批流程**：护理计划登记员 → 护理计划审核主管 → 养老护理院复核负责人
- **状态联动**：入住评估、护理计划、家属确认三块内容互相影响护理计划单状态
- **交接校验**：护理计划单进入下一步前必须校验交接信息（班次、交出人、接收人、确认时间），缺一项拦截
- **数据一致**：列表、详情、批量结果和统计统一从后端取数，确保刷新后数据一致
- **操作追溯**：完整的操作日志和交接记录，记录每一步状态变更的原因和操作人
- **状态以后端为准**：页面提示与接口返回完全一致，提供明确的错误原因

## 技术栈

- **前端**：Nuxt 3 + Vue 3 + TypeScript + Pinia
- **后端**：Rust + Rocket 框架
- **数据库**：SQLite（本地文件存储）
- **认证**：JWT Token

### 端口说明

- 前端端口：`3001`
- 后端端口：`8001`

## 快速启动

### 一、启动后端服务

```bash
cd backend

# 首次运行会自动编译并创建数据库和初始账号
cargo run
```

服务启动后访问 `http://localhost:8001`

**数据库文件**：后端启动时会自动在 `backend/nursing_care.db` 创建 SQLite 数据库文件，并自动初始化表结构和测试账号。

### 二、启动前端服务

```bash
cd frontend

# 安装依赖
npm install

# 启动开发服务
npm run dev
```

前端启动后访问 `http://localhost:3001`

## 业务流程

### 状态流转图

```
草稿(draft) ──提交──> 待审核(pending_audit) ──审核通过──> 待复核(pending_review) ──复核归档──> 已归档(archived)
   ↑                         ↓                            ↓
   └──────退回补正───────────┴────────────退回────────────┘
                            已退回(returned)
```

### 提交前校验条件

护理计划单提交审核前必须同时满足以下条件：
1. **入住评估**状态必须为「已完成」
2. **家属确认**状态必须为「已确认」
3. **护理计划内容**不能为空

### 交接信息校验

进入下一步（审核通过、复核归档）时必须填写完整的交接信息：
- 班次（早班/中班/晚班/夜班）
- 交出人姓名
- 接收人姓名
- 确认时间
- 交接内容（可选）

缺任一项都会被系统拦截，无法进入下一步。

## 页面说明

### 1. 登录页
- 路径：`/login`
- 功能：使用用户名密码登录，登录后根据角色跳转

### 2. 护理计划单列表
- 路径：`/plans`
- 功能：查看所有护理计划单，支持按状态筛选，分页显示
- 可查看字段：计划编号、老人信息、护理级别、评估状态、家属确认状态、当前状态、创建时间等

### 3. 新建护理计划
- 路径：`/plans/create`
- 权限：仅登记员可访问
- 功能：录入老人基本信息和护理计划内容

### 4. 护理计划详情
- 路径：`/plans/:id`
- 功能：查看完整详情，包括基本信息、入住评估、家属确认、交接记录、操作日志
- 根据角色和状态显示对应的操作按钮
- **退回原因**明确展示在操作日志中，说明为什么被退回
- **推进说明**：提交前会列出需要完成的事项，说明为什么还不能推进

### 5. 统计概览
- 路径：`/statistics`
- 功能：查看各状态数量、护理级别分布、班次交接统计、完成率等

## 数据一致性保障

1. **状态变更以后端为准**：所有状态变更必须通过后端接口处理，前端只展示接口返回的最新状态
2. **统一数据源**：列表、详情、统计均从同一数据库查询，确保数据一致
3. **操作后刷新**：每次操作成功后重新获取详情数据，确保显示的是最新状态
4. **刷新页面数据一致**：所有数据均存储在后端 SQLite 数据库中，刷新页面后数据不变

## API 接口说明

### 认证接口

- `POST /api/auth/login` - 登录
- `GET /api/auth/me` - 获取当前用户信息

### 护理计划单接口

- `GET /api/plans/list` - 获取列表（支持 status、page、page_size 参数）
- `GET /api/plans/:id` - 获取详情
- `POST /api/plans/create` - 创建
- `PUT /api/plans/:id` - 更新基本信息
- `PUT /api/plans/:id/assessment` - 更新入住评估
- `PUT /api/plans/:id/family-confirm` - 更新家属确认
- `POST /api/plans/:id/transition` - 状态流转（submit/resubmit/approve/reject/archive）
- `GET /api/plans/:id/logs` - 操作日志
- `GET /api/plans/:id/handovers` - 交接记录
- `POST /api/plans/batch/transition` - 批量状态流转
- `GET /api/plans/batch/list` - 批量操作记录列表
- `GET /api/plans/batch/:id/items` - 批量操作明细

### 统计接口

- `GET /api/statistics/summary` - 统计概览

### 用户接口

- `GET /api/users/list` - 用户列表

## 数据库结构

### users 表 - 用户表
- id, username, password_hash, real_name, role, created_at

### nursing_plans 表 - 护理计划表
存储护理计划单的完整信息，包括老人信息、评估状态、计划内容、家属确认状态、当前状态等。

### handover_records 表 - 交接记录表
记录每次状态推进时的交接信息。

### operation_logs 表 - 操作日志表
记录所有状态变更和编辑操作，包含操作人、操作动作、前后状态、原因等。

### batch_operations 表 - 批量操作主表
记录每次批量操作的基本信息，包括操作人、动作、总数、成功数、失败数等。

### batch_items 表 - 批量处理明细表
记录每条批量处理的明细，包括对应的计划单、成功/失败状态、失败原因、前后状态等。

## 样例数据入口

首次启动后端时会自动创建三个测试账号和 **12 条各状态的样例护理计划数据**，使用这些账号登录即可体验完整流程。

系统内置各状态样例数据：
- 草稿状态：3 条
- 待审核状态：3 条
- 待复核状态：2 条
- 已归档状态：2 条
- 已退回状态：2 条

建议测试流程：
1. 使用 `registrar1` 登录，创建一条护理计划
2. 在详情页填写入住评估和家属确认
3. 提交审核
4. 使用 `auditor1` 登录，审核通过（需填写交接信息）或退回
5. 使用 `reviewer1` 登录，复核归档（需填写交接信息）
6. 查看统计页面验证数据

**批量功能演示**：
1. 使用 `registrar1` 登录，在列表页勾选多条草稿状态的计划，点击「批量提交」
2. 使用 `auditor1` 登录，在列表页勾选多条待审核计划，点击「批量审核通过」或「批量退回」
3. 使用 `reviewer1` 登录，在列表页勾选多条待复核计划，点击「批量复核归档」或「批量退回」
4. 批量操作后查看结果面板，了解每条记录的成功/失败状态和失败原因
5. 操作后统计数据自动刷新，与列表、详情保持一致
